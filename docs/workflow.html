ITS2 Alignment Manager

How the manager turns a directory of reconstructed track files into aligned sensor parameters: how one batch is shuffled and split across parallel workers, how each worker runs an unmodified copy of the alignment module, how the per-worker network weights are averaged back into a single parameter set, and how that set becomes the starting point of the next batch.

Section 00What the manager is

The alignment module trains one small network per silicon sensor against a track-fit residual. It reads one input file and writes one archive. The manager is everything around that: it decides which data the module sees, runs many copies of it at once, and reconciles their answers into a single alignment.

The division of labour is worth stating precisely, because it is what makes the module replaceable. The module knows nothing about parallelism. It opens ./XXXXinput.root, reads the previous step's weights from ./MLPTrain_Step<n-1>/, trains, and writes MLPTrain_Step<n>.tgz. Every copy of it runs that same sequence in its own directory, unaware that seven siblings are doing the same thing on different slices of the same batch.

The manager supplies the context. It merges and shuffles the raw track files, splits the merged events into nsplit statistically independent slices, gives each worker a slice and an identical copy of the previous alignment, waits for all of them, averages the resulting per-sensor weights, and packs the average into the archive the next batch will start from. The module is therefore delivered as a frozen tarball — MODULE/<modulename>.tgz — and never edited in place.

Scope

This document covers the orchestration layer only. For what happens inside one worker — the cost function, the vertex constraint, how network weights become six rigid-body parameters per sensor — see docs/workflow.html in ALICE-ITS2-ML-Alignment-2024 and ALICE-ITS2-ML-Alignment-2025, the two source trees that are packed into that tarball.

Section 01Three repositories

The project is split across three repositories with a one-way dependency: the manager consumes the source trees, never the reverse.

RepositoryHoldsReaches the run as
…-Manager Batch driver, data-prep macros, weight-merge macro, remote-training client Checked out and run directly
…-2024 Alignment module, fixed-vertex generation MODULE/<name>.tgz
…-2025 Alignment module, self-estimated vertex generation MODULE/<name>.tgz

Which of the two source trees is in play is decided by one string in the driver, and nothing else in the manager depends on that choice: 

runAll_alignment_example.sh:38-39
modulename="v20250627-a_vtx.useAPR.hitCluster.useDCA.ver4_core.v20251024"
modulename="v20250627+a_vtx.useAPR.hitCluster.useDCA.ver4_core.v20251024"   ← this one wins

The two lines differ by one character, -a_vtx against +a_vtx, which is the 2024/2025 distinction: a vertex taken from the reconstruction against a vertex the module re-estimates from the ITS tracks themselves. The second assignment overwrites the first, so the run uses +a_vtx. Because the archive name is the only link between the manager and a particular source tree, keeping the two commented alternatives side by side is how the switch is recorded — but only the last line has any effect.

Reproducibility

The tarball name is the whole provenance record. Nothing in the manager pins the source repository to a commit, so an archive rebuilt from a moved branch keeps its name while its contents change. Tagging the source trees with the same version string that appears in modulename is what makes a past run reconstructible.

Section 02One batch, end to end

runAll_alignment_example.sh takes a single argument, a run tag, and executes ten batches in sequence. Every batch performs the same four stages and advances the alignment by one step. 

./runAll_alignment_example.sh <TAG>          # TAG names this run; all output is filed under it
Stage 1 Data preparation Shuffle the available track files, merge a random selection, split the merged events into nsplit slices.
Stage 2 Parallel training Launch nsplit module copies in the background, one per slice, each starting from the same previous alignment.
Stage 3 Weight merge Collect the last epoch's weights from every worker and average them per sensor into one parameter set.
Stage 3-1 Parameter handoff Repack the merged weights into the archive the next batch consumes as its starting alignment.

Section 03Working directories

Four directories under the checkout carry all run state. The driver resolves them once, near the top, and every later path is derived from those four variables plus the run tag. 

runAll_alignment_example.sh:29-41
homedir=$PWD

paramsdir="${homedir}/PARAMS"
moduledir="${homedir}/MODULE"

Because every path is tag-scoped below the top level, two runs with different tags coexist without colliding — but they share MODULE/ and the reference archive in PARAMS/, which are read-only during a run.

The four directories are tracked in git so that a fresh clone is already runnable, each holding a .gitignore that keeps the directory itself while excluding the archives, ROOT files and logs that land in it during a run. run_dir_maker.sh creates the same set with mkdir -p and remains correct for a workspace assembled outside a clone.

Disk

Nothing in the driver removes intermediate data. Each batch keeps its split inputs under ALIGN/<TAG>/step<b>/, every worker's archive and its unpacked copy under RESULT/<TAG>/result_step_<b>/, and a further copy of each worker's tree in align_worker_<ns>/buffer_step<b>/. A full ten-batch run therefore holds ten batches of split ROOT files and eighty worker archives at once.

Section 04Stage 1 — data preparation

Two ROOT macros run back to back. The first builds one merged file from a random selection of the available runs; the second scatters its events into the slices the workers will train on.

DataRandomMerge.C — select and merge

The macro holds an explicit list of input files — the current list is ten run00539884 files with DCA information — and a directory on external storage where they live. It shuffles the list with TRandom3 seeded by the batch number, symlinks the first few into MasterData/, and hadds them into one file. 

runAll_alignment_example.sh:69 → RUN/MasterDataScript/DataRandomMerge.C
root -l -b -q DataRandomMerge.C"($bcnt,20)"

  random(seed=$bcnt, maxSelection=5)   # shuffle, symlink 5 files into MasterData/
  ls MasterData > MasterData_$bcnt.lst
  hadd alignment-input-data_$bcnt.root MasterData/…

The second argument, nMAXfiles = 20, caps the merge; the selection is capped earlier and harder by the maxSelection = 5 hard-coded in the call to random(), so five files are merged regardless. Both shuffles are seeded by the batch number, which makes the whole selection reproducible: batch 3 of one run sees exactly the files batch 3 of any other run sees.

DataSplit.C — scatter into slices

The split is per event and uniform. For each event in the merged tree the macro draws splitIndex = rseed.Uniform(0, nsplit) and copies the whole event — every track, every cluster, the vertex fields — into that slice's output tree. Nothing is duplicated across slices and nothing is selected out, so the slices are disjoint samples of the same population. 

RUN/MasterDataScript/DataSplit.C:151
DataSplit(seed=$bcnt, nsplit=8, bid=0)

  o2::base::GeometryManager::loadGeometry()      # O2 geometry, L2G matrix cache
  for each event:
      splitIndex = Uniform(0, nsplit)            # uniform, per event
      copy event → step$bcnt/alignment-input-data-split<splitIndex>.root

Each slice file also carries two monitoring histograms, hNClusterByTrack and hNTrackByEvent, so the slice populations can be compared after the fact. The macro loads the O2 geometry and fills the local-to-global matrix cache, which is what lets it resolve a ChipID into layer, half-barrel, stave, half-stave and module.

The prepared batch, its two logs and the file list are then moved wholesale into the run's worker area as ALIGN/<TAG>/step<b>/.

Section 05Stage 2 — parallel training

The workers are ordinary background processes on one machine. Each owns a directory, a slice of the batch, and its own unpacked copy of the module; none of them communicates with another. Parallelism here is data parallelism with a single synchronization point at the end.

What the driver does per worker

Before the batch loop begins, each worker directory is created once and the module tarball is unpacked into it. Inside the loop the driver only has to attach the slice and the previous alignment, then launch: 

runAll_alignment_example.sh:93-116, per worker ns
cd ${alignworker}/align_worker_$ns/${modulename}

rm -f XXXXinput.root
ln -s ${alignworker}/step$bcnt/alignment-input-data-split${ns}.root XXXXinput.root

# batch 1 seeds from the tracked reference; later batches from the previous batch's output
if [ $bcnt -eq 1 ] ; then
  cp ${paramsdir}/MLPTrain_Step${input_step}.tgz .
else
  cp ${paramsdir}/${TAG}/MLPTrain_Step${input_step}.tgz .
fi
tar -zxvf MLPTrain_Step${input_step}.tgz

./process_all_master.sh ${TAG} ${start_step} ${end_step} &    # background
sleep 15s                                             # stagger, not a barrier

XXXXinput.root is the module's fixed input name; the symlink is the entire interface for data. The sleep 15s between launches staggers process startup so eight ROOT sessions do not open the geometry at the same instant — it is not a synchronization primitive. The real barrier is the bare wait after the loop, which blocks until all eight background jobs have exited.

Inside a worker

From here the manager is out of the picture. The module's own three-script chain takes over, and the C preprocessor macros in YMLPParallel.h — not any manager variable — decide the job size. 

process_all_master.sh <TAG> <stepI> <stepF>
  └─ alienv load O2/latest                      # O2 environment
     process_all_train.sh
       ├─ run_profile_beam.C                    # writes YMLPBeamProfile.h
       └─ for nStep in stepI..stepF:
            # batch_train is regenerated per step, then sourced by ROOT
            .L ./Ymlp/src/YDetectorGeometry.cxx
            .x run_train_circle.C(nStep)        # the training itself
            tar -zcvf MLPTrain_Step<nStep>.tgz MLPTrain_Step<nStep>
Where the knobs live

nDATA, nEPOCH, jparallel and nCORE are #defines compiled into the module at run time. Changing the number of events or epochs means editing the source tree and rebuilding the tarball — the manager cannot override them, and does not try to.

Collecting the results

Once the barrier clears, each worker's archive is renamed with its worker index and moved to the run's result container, and the unpacked tree is set aside in a per-batch buffer: 

runAll_alignment_example.sh:128-132
mv MLPTrain_Step${nStep}.tgz MLPTrain_Step${nStep}-aw${ns}.tgz
mv MLPTrain_Step*.tgz ${resultcontainer}/result_step_${bcnt}/
mkdir ../buffer_step$bcnt
mv MLPTrain_Step* ../buffer_step$bcnt/

The -aw<ns> suffix is what carries worker identity forward; it is the only label the merge stage has to work with.

Section 06Stage 3 — weight merge

Eight workers have produced eight opinions about where every sensor sits. The merge reduces them to one by taking, for each sensor and each network weight, the unweighted arithmetic mean across the workers that reported.

Gathering

The driver unpacks each worker's archive, walks into its weights/ directory and picks the most recently modified weights_Epoch* file — the last epoch the worker completed — then files it under a zero-padded worker index: 

runAll_alignment_example.sh:143-152
tar -zxvf MLPTrain_Step${end_step}-aw${ns}.tgz
cd MLPTrain_Step${end_step}-aw${ns}/weights
weightfile=`ls -altr | grep "weights_Epoch" | awk '{print $9}' | tail -n1`
splitindex=`printf "%.3d" ${ns}`
cp ${weightfile} …/RUN/MergeParamsScript/weights_step${bcnt}/weights_n${splitindex}.txt

The file name is the channel: WeightsMerge.C recovers the worker index by stripping weights_n and .txt from each name it finds, and marks that index present. A worker that crashed leaves no file, its index stays absent, and the merge proceeds over the survivors — silently, with the divisor reduced accordingly.

Averaging

Each weight set is loaded into a TH2D spanning all 24 120 chips on one axis and the network parameters on the other. The merge is a single loop over both axes: 

RUN/MergeParamsScript/WeightsMerge.C:391-400
for each chip ic, for each weight j:
    weight = 0
    for each present patch p:
        weight += NetworkWeights[p].hWeights(ic, j) / NetworkWeights.size()
    BaseNetworkWeight.hWeights(ic, j) = weight

There is no weighting by track count, by residual quality or by convergence. A worker that saw an unusually thin sample of a given sensor contributes to that sensor exactly as much as one that saw a rich sample. This is the assumption Figure 2 rests on: because the slices are uniform random partitions of the same batch, the samples are exchangeable and a plain mean is the natural estimator.

Silent degradation

Absence and failure look identical here. If a worker dies before writing its last epoch, the merge still runs, still produces a well-formed parameter file, and reports only through the weights n#<p> attached lines in alignment-params-merge.log.<b>. Counting those lines is the check that the batch actually had the statistics it was supposed to have.

Outputs

Alongside the merged parameter file, the macro writes a monitoring tree that carries, per sensor, both the merged parameters and each individual worker's parameters, plus the global position of the sensor before and after the correction — Sx, Sy, Sr, Sφ, Sz and the corresponding deltas. That is what makes worker-to-worker spread inspectable after the fact.

Section 07Stage 3-1 — parameter handoff

The merged weights are a bare text file; the module expects a complete archive. The handoff builds one — and the way it builds it has a consequence that is easy to miss. 

runAll_alignment_example.sh:170-178
mkdir -p PARAMS/${TAG}
cd PARAMS
cp MLPTrain_Step${BASESTEP}.tgz ${TAG}/          # always the reference, never the previous batch
cd ${TAG}
tar -zxvf MLPTrain_Step${BASESTEP}.tgz
mv MLPTrain_Step${BASESTEP} MLPTrain_Step${end_step}
rm MLPTrain_Step${end_step}/weights/weights.txt
cp …/step$bcnt/weights_merge_step$bcnt.txt MLPTrain_Step${end_step}/weights/weights.txt
tar -zcvf MLPTrain_Step${end_step}.tgz MLPTrain_Step${end_step}

Whether that is intended depends on what those two files mean to the module. If UpdateSensorsList.txt is a static roster of which sensors may move, re-seeding it is harmless and arguably safer. If the module updates it as training proceeds — and run_train_circle.C does write a fresh one into every step's output — then that per-step evolution is discarded at the batch boundary, and only the within-batch steps see it. With NSTEPBYBATCH = 1 there are no within-batch steps, so it is discarded every time.

Worth confirming

This is the one place where the manager's bookkeeping can silently disagree with the module's expectations. Comparing UpdateSensorsList.txt inside a worker's output archive against the copy in PARAMS/<TAG>/MLPTrain_Step<n>.tgz settles it in one command.

Section 08Step numbering

The module numbers its training steps globally and expects step n to find step n-1 next to it on disk. The manager keeps that numbering coherent across batches with three derived variables: 

runAll_alignment_example.sh:90-92
input_step = BASESTEP + (bcnt - 1) * NSTEPBYBATCH        # archive to start from
start_step = BASESTEP + (bcnt - 1) * NSTEPBYBATCH + 1     # first step this batch trains
end_step   = BASESTEP +  bcnt      * NSTEPBYBATCH         # last step this batch trains
bcntinput_stepstart … endReadsProduces
1900901 … 901PARAMS/Step900.tgzPARAMS/<TAG>/Step901.tgz
2901902 … 902PARAMS/<TAG>/Step901.tgzPARAMS/<TAG>/Step902.tgz
⋮⋮⋮⋮⋮
10909910 … 910PARAMS/<TAG>/Step909.tgzPARAMS/<TAG>/Step910.tgz

BASESTEP = 900 is not arbitrary: it is the step number of the reference archive committed to the repository, PARAMS/MLPTrain_Step900.tgz. A run therefore picks up where that reference left off, and the numbering stays globally meaningful across runs.

What NSTEPBYBATCH controls

With NSTEPBYBATCH = 1 each batch trains exactly one step, so start_step == end_step and every step is followed by a merge. Raising it makes each worker chain several steps locally — process_all_train.sh loops stepI … stepF, and each of those steps reads the previous step's weights from the worker's own directory — before the workers are merged.

The parameter therefore sets how much the workers are allowed to drift apart before being reconciled. It trades communication for independence: one merge per step keeps the eight estimates tightly coupled; three steps per merge lets each worker follow its own slice further on its own. Only end_step is ever merged — the intermediate steps exist only inside the worker.

Section 09The distributed variant

Sizing

nsplit × nCORE is the CPU the run wants, and nsplit also divides the batch, so raising it buys parallelism at the cost of statistics per worker. With nDATA = 50 000 each worker wants that many events in its own slice, which sets the floor on how much data one batch must merge.

Section 11Gaps in the checked-in tree

The repository is a record of a pipeline that runs on a specific machine, not a self-contained distribution. The following are differences between what the scripts assume and what the tree provides, listed so that a reader does not have to rediscover them. None of them is a correction being proposed here.

Would stop a run on a fresh clone

DataRandomMerge.C:22 · runAll_alignment_example.sh:13 · process_all_master.sh:9

dataSetDir and o2dir are absolute paths to one workstation's storage and O2 build. They are the two values a new machine must change first.

Fragile, but works in place

runAll_alignment_example.sh:128-131

Inside the per-step loop, the rename is followed by mv MLPTrain_Step*.tgz — a glob that matches every archive present, not only the one just renamed. It is harmless while NSTEPBYBATCH = 1 leaves a single archive in the directory; with more steps per batch, the first iteration moves the archives the later iterations expect to rename.

mkdir ../buffer_step$bcnt in the same loop has no -p, so it reports an error on every iteration after the first.

runAll_alignment_example.sh:149

The last-epoch weight file is selected by parsing field 9 of ls -altr. This depends on the ls output format, and picks by modification time rather than by epoch number.

DataSplit.C:33 · module run_train_circle.C:33,39,43,48

Several mkdir calls omit -p, so a re-run over an existing directory writes an error to the log without failing the job.

RUN/MasterDataScript/runDataPrep.sh:4 vs runAll_alignment_example.sh:21

The standalone data-prep script uses nsplit = 10 where the driver uses 8. Slices prepared by one are not a matched set for the other.

In the distributed path only

RUN/TrainScript/run_train_circle.C:11

SetSourceDataName(strData) refers to an identifier that is not declared; the parameter carrying that value is named strRoot. The macro would not compile as written.

Train.sh:129 · runMergeParams.sh:22,26,30

Uploads are written as ssh -p 22315 ./file user@host:/path, which passes the local file as the remote command rather than copying it. The matching download on runMergeParams.sh:14 correctly uses scp.

Train.sh:135

The result-report URL contains unquoted & characters, so the shell splits it into background jobs and only wget …?wid=$wid is actually requested. The result= parameter also names MLPTrain_Step6.tgz literally rather than the step just completed.

Reading order

For anyone picking this up: start at runAll_alignment_example.sh and read it top to bottom — it is 182 lines and contains the whole orchestration. Everything else in RUN/ is a leaf that it calls.
